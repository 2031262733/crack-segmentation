# 裂缝分割复现：原理、运行与调试笔记

> 对应仓库代码：`train.py` / `evaluate.py` / `models.py` / `losses.py` / `dataset.py`
> 数据：CFD（CrackForest Dataset），9603 张训练、1695 张测试，448×448 路面影像 + 像素级裂缝掩膜。

---

## 1. 这个任务到底是什么

输入一张路面影像，输出**同尺寸的 0/1 掩膜**，1 表示该像素属于裂缝。

为什么用分割而不是检测框：裂缝是宽度只有几个像素的细长结构，检测框只能给出“这块有裂缝”，给不出走向、宽度和面积。巡检场景真正要的是长度、面积、走向，这些只能从像素级掩膜里算出来（骨架化后累计长度、面积占比）。所以这个岗位 JD 里写的“缺陷识别”，落到路面/结构物上，主流做法就是语义分割。

一句话串起整条链路：

```
影像 → 归一化 → 编码器提特征 → 解码器还原分辨率 → 逐像素概率 → 阈值二值化 → 骨架化/面积统计
```

## 2. 两个模型，各解决什么问题

### 2.1 U-Net：最稳的基线

结构是“编码器—解码器 + 跳跃连接”：

- 编码器：4 次 3×3 卷积 + 2×2 池化，通道 32→64→128→256→512，分辨率 256→16。每下采样一次，感受野变大，语义变强，但空间细节丢一次。
- 解码器：每级双线性上采样回上一级尺寸，和编码器**同分辨率**的特征在通道维拼接（skip connection），再过两层卷积。
- 输出：1×1 卷积压到 1 通道，得到每个像素的裂缝得分。

**skip 为什么关键**：裂缝宽度常常 1–3 个像素。经过 4 次池化，这条线在 16×16 的特征图上几乎消失；跳跃连接把编码器里还保留着边缘位置的高分辨率特征直接送到解码器，等于告诉解码器“线大概在这几个像素上”，解码器只负责把它拟合准。没有 skip 的 FC 型分割网络在这种细结构上会糊成一片。

### 2.2 DeepCrack：多尺度 + 深监督

DeepCrack（Liu et al., Neurocomputing 2019）用 VGG16 做编码器，在 5 个 stage 的末端各接一个 1×1 卷积得到 5 张侧输出（side1–side5），全部双线性上采样回原图尺寸，再把这 5 张拼起来用 1×1 卷积融合成最终结果。

它想解决的是 U-Net 的一个现实问题：**深层特征语义强但会把细线“抹掉”，浅层特征位置准但语义弱**。DeepCrack 让每个尺度都直接输出一张裂缝图，训练时每一张都要和标签算损失（deep supervision，深监督），于是：

- side1/side2（浅层，分辨率高）：负责把裂缝的**位置和连续性**学出来；
- side4/side5（深层）：负责判断“这到底是不是裂缝”，抑制路面纹理、阴影、车道线这类假阳性；
- fuse 层学的是“该信谁”——在不同尺度之间做加权融合，而不是人工定权重。

这里和原论文有一处**主动改写**：原论文侧输出用加权交叉熵，我改成 `BCE + Dice` 的联合损失，原因是 CFD 里裂缝像素只占 1%–2%，纯 BCE 会让模型倾向于全预测背景（loss 很低但 F1 接近 0），Dice 直接优化重叠率，能把这种退化拉回来。

### 2.3 损失函数

对每个输出（5 个 side + 1 个 fuse）：

```
L_i = BCEWithLogits(logit_i, y) + Dice(prob_i, y)
L   = 1.0 * L_fuse + w * Σ L_side        # w 默认 0.5，DeepCrack 实测用 0.25（原因见 6.1）
```

- **BCE**：逐像素二分类，梯度稳定，收敛快；
- **Dice**：`2|P∩G| / (|P|+|G|)`，对前景稀少不敏感，专门治“全黑输出”；
- **权重**：侧输出是辅助监督，最终结果以 fuse 为准，所以 fuse 权重 1.0；w 决定总梯度尺度，w×N_side 不宜超过 1。

### 2.4 指标怎么算

固定阈值 t，把概率二值化：

```
TP = pred=1 且 gt=1     FP = pred=1 且 gt=0     FN = pred=0 且 gt=1
Precision = TP/(TP+FP)   Recall = TP/(TP+FN)
F1 = 2PR/(P+R)           IoU = TP/(TP+FP+FN)
```

- 我同时报 **micro**（把所有测试图像的 TP/FP/FN 累加再算，面积大的图权重大）和 **per-image mean**（每张图算一次 F1 再平均，小裂缝图权重相同）。裂缝论文常用后者，两者都列出来避免挑好看的。
- 阈值不是拍脑袋定的：扫 0.10–0.90（步长 0.05），报 `@0.5` 和“最优阈值”两组数，最优阈值要在报告里写清楚是在哪份数据上选的，否则就是变相调参。

## 3. 数据与预处理

- 来源：HuggingFace `varcoder/crack-segmentation-dataset`（CFD 的 image/mask 成对版本，parquet 存储）。
- 规模：train 9603 / test 1695，原图 448×448。
- 掩膜是 JPG，边缘有压缩灰边，所以统一用 `mask > 0.5` 二值化，不保留灰阶。
- 训练时缩放到 256×256（不是随机裁剪）：CFD 的裂缝经常贯穿整幅图，裁剪会把线截断，模型学不到连续性。
- 增强只做**不改变几何语义**的操作：水平/垂直翻转、90° 旋转、亮度 ±20%、对比度 ±20%。没有做弹性形变和 CutMix——裂缝是拓扑结构，乱变形会造出自然界不存在的分叉。
- 归一化用 ImageNet mean/std，因为 DeepCrack 的 VGG16 是 ImageNet 预训练权重，输入分布要对齐。

## 4. 训练配置

U-Net 与 DeepCrack 用的是**不同的训练配方**，原因在 6.1 里写了：DeepCrack 六个输出来自同一批梯度，尺度是单头的 2–3 倍，用 U-Net 那套直接发散。

| 项 | U-Net | DeepCrack |
|---|---|---|
| 优化器 | AdamW，lr 1e-4，wd 1e-4 | AdamW，lr 1e-4，wd 1e-4 |
| 调度 | Cosine，最低 lr×0.01 | 同左 |
| 精度 | AMP（fp16） | **fp32**（关 AMP） |
| 损失 | BCE+Dice，单头 | BCE+Dice ×6，side 0.25 / fuse 1.0 |
| BN | 正常更新 | **冻结**（用 ImageNet 统计量） |
| 梯度裁剪 | 5.0 | 1.0（每轮裁剪前范数 60–140） |
| batch | 4 | 4 |
| 轮数 | 12 | 10 |
| 验证集 | train 里按种子 42 划 10% | 同左 |
| 选模 | 验证集 F1 最高存 `best.pt` | 同左 |

为什么 BatchNorm 要冻结：预训练 VGG16 的 running mean/var 是在 ImageNet 的大批量上统计出来的；batch=4 时每步的批统计噪声很大，几百步就能把 running stats 带偏，接着训练集和验证集的行为分叉。冻结之后 BN 退化成固定的逐通道仿射，训练立刻稳定。代价是失去批统计自适应，但裂缝这种单通道纹理任务不需要它。

## 6. 怎么调试（踩过的坑按症状列）

| 症状 | 真实原因 | 处理 |
|---|---|---|
| 第 2 个 batch 就 `CUDA out of memory`，但 `nvidia-smi` 显示还有 6 GB 空闲 | 8 GB 卡 + 桌面/浏览器占用 + 分配器碎片；`expandable_segments` 未开 | batch 8→4，开 `expandable_segments:True`，训练前 `torch.cuda.empty_cache()` |
| 训练跑着跑着进程没了，日志末尾是 `OSError: [WinError 1455] 页面文件太小`，栈顶在 worker 的 `import torch` | Windows 用 spawn 起 dataloader worker，每个 worker 都要重新加载 CUDA 版 torch（约 1 GB 提交内存）；16 GB 内存 + 小页面文件时提交量直接超限 | `--workers 0`（本项目默认）；或把系统页面文件调大到 16 GB 以上；内存 ≥32 GB 再开 2–4 worker |
| 第一个 iteration 卡 40–60 秒，像死机 | `cudnn.benchmark=True` 在为每一种卷积形状做算法搜索 | 正常现象，只会发生一次；不想等就关掉 benchmark |
| 换成 `channels_last` 想加速，结果 U-Net 反而慢 2.6 倍（93→36 img/s） | 小通道数 + BatchNorm 的布局转换开销大于收益 | 保持默认 NCHW；布局优化要按模型实测，不能想当然 |
| loss 一直在 0.02 左右，F1≈0，预测全黑 | 裂缝像素占比 1%–2%，BCE 退化解 | 加 Dice；或 BCE 加 `pos_weight`；先在小样本上过拟合验证链路 |
| 训练 loss 降、验证 F1 0.7 就不动了 | 学习率后期太大 / 增强过强 | cosine 退火到 1e-6；降低亮度对比度扰动幅度 |
| 验证集很好、测试集掉 5 个点 | 同一条路的多张图被分到 train/test，近邻泄漏 | 按**路段/来源**划分，而不是随机按图划分 |
| 预测有大量细碎噪点 | 固定 0.5 阈值偏低 + 无后处理 | 阈值扫描；连通域面积过滤；骨架化后再量长度 |
| `DataLoader` 每个 batch 几秒，GPU 利用率个位数 | 图像解码在 CPU 侧成瓶颈 / worker 太少 | `num_workers=3–4`、`pin_memory=True`、`persistent_workers=True`；数据放 SSD |
| Windows 上 `cv2.imread` 返回 None | 路径含中文，OpenCV 不支持非 ASCII 路径 | 用 `PIL.Image.open`（本项目全程用 PIL），或先 `cv2.imdecode(np.fromfile(...))` |
| 同一份代码换机器 loss 变 NaN | AMP 下梯度溢出 | `GradScaler` 已开；仍溢出就关 AMP 或把 lr 减半 |
| DeepCrack 训练 loss 从第 3 轮开始回升，第 7 轮直接 NaN | 6 个输出求和 → 梯度尺度是单头的 2–3 倍；fp16 下 Dice 的全局求和容易溢出；预训练 BN 在小 batch 下被带偏 | 见 6.1，四个动作一起改 |

### 6.1 一次真实发散：DeepCrack 第 7 轮 NaN

第一次训练（AMP、side 权重 0.5、BN 正常更新、lr 1e-4）的曲线：

| epoch | train loss | val F1 |
|---|---|---|
| 1 | 2.68 | 0.655 |
| 2 | 2.37 | 0.646 |
| 3 | 2.66 | 0.460 |
| 4 | 3.61 | 0.413 |
| 5+ | 5.15 → … | 崩到 0 |
| 7 | **nan** | — |

判断过程：

1. **不是数据问题**——U-Net 用同一份数据和同样的 loss 一直很稳，问题出在模型/训练配方。
2. **不是 lr 太高**——把 lr 从 1e-4 降到 5e-5，曲线形状一模一样，只是晚两轮崩。说明是某个会积累的量在恶化，不是单步步长太大。
3. **锁定“梯度尺度”**：这个 loss 是 `fuse + 0.5×Σ(side1..5)`，总系数 3.5；U-Net 是 1.0。AdamW 的更新量近似只跟 lr 有关，但 fp16 的动态范围和 Dice 的全局求和（262144 个元素相加）扛不住 3.5 倍的量级。
4. **加上 BN**：预训练 VGG16 的 running stats 被 batch=4 的批统计替换，几百步后 train/eval 行为分叉，验证 F1 掉、训练 loss 还在涨，正是这个症状。

四个动作一起改（只改一个都不够）：

| 改动 | 原因 |
|---|---|
| 损失移出 autocast，`logits.float()` 后再算 | 消除 fp16 求和溢出 |
| `--amp 0`（整个训练 fp32） | 15 M 参数的小模型，fp32 只慢 ~25%，但不会再 NaN |
| `--side-weight 0.25` | 总系数 3.5 → 2.25，梯度回到可控范围 |
| `--freeze-bn 1` + `--clip 1.0` | BN 不再漂移；每步裁到 1.0（原始范数 60–140） |

改完的结果（10 轮）：loss 单调下降 1.68 → 1.18，val F1 0.656 → **0.718**，没有一次非有限值。这个对比说明：**发散时先量梯度范数和 loss 的量级，再决定关精度、减权重还是冻结 BN；只调 lr 往往只是把崩溃推迟两轮。**

调试的通用顺序（也是面试可以讲的排查思路）：

1. **先证明链路通**：拿 8 张图、关增强、过拟合到 F1>0.95。过拟合不了就是代码 bug（标签没对齐、mask 没二值化、loss 用错），不是调参问题。
2. **再看数据**：把 image 和 mask 叠在一起可视化，确认裂缝位置对齐、没有被 resize 插值糊掉。
3. **再看梯度**：打印每个 stage 的梯度范数，某层长期为 0 说明它没参与学习（比如侧输出初始化把 sigmoid 推到饱和）。
4. **最后才调参**：lr → 增强强度 → 损失权重，一次只动一个变量。

## 7. 面试怎么讲（3 分钟版）

> “我在 CFD 上复现了 DeepCrack，并写了 U-Net 做对照。U-Net 是编码器-解码器加跳跃连接，靠 skip 把高分辨率边缘送回解码器；DeepCrack 用 VGG16 的五个 stage 各出一个侧输出，上采样后融合，训练时每个尺度都加监督，浅层负责定位、深层负责判别真假裂缝。损失用 BCE+Dice，因为裂缝只占 1%–2%，纯 BCE 会退化成全背景。数据 9603 张训练、1695 张测试，256 输入，10–12 轮。最后 DeepCrack 测试集 F1 0.730、IoU 0.575，比 U-Net 高 2.5 个点，单张 256² 推理约 4.6 ms。踩过的坑：8 GB 显存下 OOM、cudnn benchmark 首次搜索、channels_last 反而变慢，还有 DeepCrack 深监督在 fp16 下第 7 轮变 NaN，最后靠损失转 fp32、降侧输出权重、冻结 BN、梯度裁剪 1.0 一起解决。”

可能被追问的点：

- **为什么不用 Transformer / SAM？** 数据量 1 万张、目标是无纹理的细线，CNN 的归纳偏置更合适；SAM 需要提示且推理重，巡检要的是实时。
- **为什么 F1 不是 mAP？** mAP 是检测指标，分割看像素重叠，IoU/F1 才是标准口径。
- **怎么用到无人机影像上？** 正射图切片（滑窗 + overlap）→ 逐片推理 → 拼接概率图 → 阈值 + 连通域过滤 → 骨架化量长度；切片边缘用 overlap 加权融合，避免接缝处断裂。
- **为什么阈值选最优的，不算作弊吗？** 报告里同时给 @0.5 和最优阈值，并说明最优阈值只在验证集上选，测试集只评估一次。

## 8. 结果

测试集 1695 张，输入 256×256，单次运行（seed 42），阈值 0.50。

| 模型 | 参数量 | Precision | Recall | F1 | IoU | 每图平均 F1 | FPS（bs=1） |
|---|---|---|---|---|---|---|---|
| U-Net（从头训，12 轮） | 7.8 M | 0.712 | 0.697 | 0.705 | 0.544 | 0.574 | 238 |
| DeepCrack（VGG16，10 轮） | 14.7 M | 0.711 | 0.750 | **0.730** | **0.575** | 0.590 | 216 |

- 阈值扫描的最优点对两个模型都是 0.50，所以 `@0.5` 与 `@最优` 一致；这本身是个好信号——概率分布没有出现双峰错位。
- DeepCrack 的 Recall 明显高（0.750 vs 0.697），说明多尺度侧输出确实把细、弱裂缝捡回来了；代价是参数量翻倍、速度慢 10%。
- 每图平均 F1 比 micro F1 低 13 个点：CFD 里有一批几乎没裂缝的图，只要误检一小段，单图 F1 就会掉到 0，均值被这些图拉低。汇报时两个数都要给，只给 micro 会显得在挑好看的。
- 与 DeepCrack 原论文（CFD 上约 0.80 F1）的差距来自预算：256 输入、10–12 轮，而原论文用 448 输入、训练到收敛。两条验证曲线在最后一轮都还在涨。

> 定性误差图（原图 / 真值 / 预测 / 绿 TP、蓝 漏检、红 误检）由 `evaluate.py` 写入 `results/<model>/overlays/`；训练曲线由 `make_figs.py` 输出到 `docs/curves.svg`。仓库里不放大图。

## 9. 和岗位的关系

这个复现覆盖了 JD 里的三件事：**图像增强**（数据增强 + 归一化）、**目标检测/缺陷识别**（裂缝分割、多尺度特征、深监督）、**工程落地**（切片推理、阈值与后处理、FPS 评估）。无人机影像拼接和三维重建是另外两个仓库的复现内容，这条线负责“看到缺陷并定位到像素”。
